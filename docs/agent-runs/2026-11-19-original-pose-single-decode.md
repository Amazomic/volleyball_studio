# 2026-11-19 · Оригинальные кадры RTMPose без второго декодирования

- Основа: `origin/develop` `3fe1b0ea34da5567cf7d25004bc5fc26fa1c0052`; отдельный worktree `perf/20261119-pose-original-single-decode`. Основную рабочую копию пользователя, её временные файлы, видеозаписи, кэши и модели не изменяли.
- Владелец декодирования: `rust/volley-media/src/raw_decoder.rs`, `rust/volley-media/src/raw_decoder/shared.rs` и `shared/tests.rs`. Единый FFmpeg `fps=30` создаёт три синхронных выхода: 512×288 gray для VBallNet, 640×360 RGB для RF-DETR и **RGB24 исходного разрешения** для RTMPose. Отдельный UNIX-сокет с ограниченным каналом, контроль индексов окон и EOF, guard на исходный RGB-кадр до 32 МиБ. Нативные девятикадровые окна передаются через `Arc<Vec<u8>>`: позы сохраняют ссылки на диапазоны байтов без копирования каждого полного RGB-кадра. Не создаются полноформатные сырьевые кэши всего матча. На слишком большом исходном кадре остаётся прежний путь RTMPose с отдельным декодированием.
- Владелец позы: `rust/volley-app/src/pose_inference/stream.rs` и тесты; `inference_full/joint.rs`, `studio_pipeline.rs`. Вместо кропов из уменьшенного кадра используются исходные пиксели и нормализованные координаты обнаружений RF-DETR. Сохранены прежняя интерполяция только между измеренными рамками, отложенная публикация до SHA-верификации fusion, GPU-batch RTMPose до 8 игроков, контроль `pixel_source_version`, `pixel_dimensions`, `coordinate_system`, схема `volley-native-gpu-pose/1`. Если RTMPose отключён или выбран отдельный режим анализа, источник для VBallNet/RF-DETR остаётся прежним, без третьей ветви декодирования. В прогрессе основного анализа RTMPose отображается как часть совместного потока.
- Контроль пикселей: `native_pose_source_has_original_decoder_pixels_and_synchronized_frames` сравнил SHA-256 каждого RGB24 кадра с прежним `decode_original_frames()` при поворотах 0° и 90°: PASS. Проверены native размеры, количество кадров, индексы и хвост декодирования.
- Реальный A/B CUDA (RTX 5070 Ti Laptop GPU, WSL Ubuntu-25.04, ONNX Runtime CUDA, без лимита GPU-памяти, 4 CPU threads, профиль `cargo test`): из `examples/gtu_20250316_002.mp4` (1920×1080) извлечён только для теста фрагмент с позиции 28 с длиной 4 с; фактически 125 decoded frames / 117 pose samples / 1334 individual pose crops. Исходное видео не менялось. Два A/B-прогона с финальным `Arc`-буфером: порядок **старый → новый**: 25,007 с → 21,249 с (15,03% быстрее); порядок **новый → старый**: 24,724 с → 23,654 с (4,53% медленнее внутри этой пары). Это подтверждает влияние очередности/прогрева; сравнение одинаковых позиций запуска между двумя парами даёт приблизительно 1,1% и 10,2% выигрыша. **Гарантированное ускорение не установлено** на столь коротком фрагменте. Числа отражают GPU+RTMPose, без сборки и подготовки тестовых кадров; не экстраполировать на полный матч. Первоначальное одиночное A/B-показание -23,44% оказалось смещено прогревом и не используется как оценка результата.
