# Контракт завершения задач: ветка → develop → работающая Studio

Применяется к **каждой** задаче и **каждому** агенту Volleyball Studio — одиночной и параллельной работе, коду, UI и документации. См. также [AGENTS.md](../AGENTS.md), [координацию агентов](AGENT_PARALLEL_WORKFLOW.md) и [развёртывание](RUST_DEPLOYMENT.md).

## 1. Разработка только в изолированной ветке

1. До записи проверить `git status --short --branch`, `git log -5 --oneline`, `git worktree list --porcelain`, `git rev-parse HEAD`, локальные и remote-ветки, чужой WIP. Не изменять чужие файлы.
2. Создать **новую локальную ветку** `codex/<run-id>/<task-id>` от актуального `origin/develop` и **отдельный абсолютный worktree**. Код, тесты и коммиты задачи — только в нём. Не редактировать и не коммитить непосредственно в `develop`, `master` или deployment worktree, даже если задача небольшая.
3. При нескольких агентах каждому выделять отдельную ветку/worktree, `base_sha`, `write_paths` и изолированные build/test/runtime данные. Пересекающиеся изменения и общие файлы назначает один координатор. Не использовать чужие worktree.
4. Не пушить незавершённые task-ветки в `develop`; task-ветки локальные, если пользователь прямо не попросил PR/публикацию.

## 2. Последовательная интеграция

1. В task-ветке провести регрессию, целевые тесты и полный локальный gate по [TESTING.md](TESTING.md) для изменений приложения. Документы проверить на корректные ссылки и `git diff --check`. Проверить diff и сделать короткий коммит.
2. Один **интегратор** принимает готовые коммиты последовательно, в отдельном чистом worktree от актуального `origin/develop`. Merge или cherry-pick — только после проверки base SHA, владельцев файлов, совместимости, наличия всех изменений и новых тестов. Одновременно два агента не сливают ветки и не пушат `develop`.
3. Перед публикацией интегратор ещё раз проверяет актуальный remote HEAD. Если `develop` продвинулся, пересобрать интеграционный кандидат поверх него и повторить затронутые проверки. Никаких `reset --hard`, `clean`, общего `stash`, force push или перезаписи пользовательского WIP.
4. **В `develop` попадают только полностью принятые и протестированные задачи.** Изменения публикуются обычным fast-forward push **только в `origin/develop`**, затем немедленно развёртываются согласно следующему разделу.
5. **Запрещено создавать commit, merge или push в `master` без прямого указания пользователя.** Ни «готовый релиз», ни правка документации релиза не служат подразумеваемым разрешением.
6. Если другой агент редактирует checkout `develop`, не трогать эти изменения: интегрировать в собственном изолированном worktree с проверкой конкурентных изменений или сохранить готовую task-ветку до безопасной интеграции.

## 3. Обязательная пересборка и запуск после push

1. Для запущенной Studio использовать **отдельный чистый Git-клон** (не task-worktree и не общий checkout с незавершёнными изменениями), где активна именно локальная ветка `develop` и `HEAD` совпадает с `origin/develop` на точном опубликованном SHA. Запрещён запуск из `master`, task-веток, detached HEAD и отставшего `develop`. Git не позволяет безопасно использовать одну и ту же локальную ветку `develop` сразу в двух worktree; отдельный клон сохраняет чужой WIP и содержит Git-метаданные, читаемые из WSL. До запуска проверить полноту моделей и зависимости в этом клоне.
2. Собрать релиз Rust из этого SHA (включая актуальные статические ресурсы/WASM по правилам запуска), даже при изменении одной документации, если задача объявляется завершённой.
3. Перед остановкой проверять владельца процесса и `/internal/rewrite-status`: `shutdown_safe=true` и `active_jobs=[]`. При активных задачах, неизвестном процессе, зависшей остановке, неудачной сборке или недоступном развёртывании — не заявлять завершение; не убивать чужие PID.
4. Запустить/перезапустить штатным launcher. Проверить `GET /studio` = 200, `/internal/rewrite-status` = 200, владельца PID и **показанный в HTML SHA сборки**, совпадающий с `origin/develop`; проверить затронутый сценарий. Вновь созданный commit после сборки требует новой сборки и проверки.
5. Push, зелёные тесты или скомпилированный файл без работающего экземпляра **не являются выполнением задачи**. При блокировке сообщить «Не завершено: ...» с SHA, причиной и следующим безопасным действием.

### Самостоятельное устранение препятствий развёртыванию

- **Без ручного шага от пользователя:** ни одна задача не заканчивается формулировкой «осталось обновить запущенную Studio», «примените изменения сами» или только ссылкой на GitHub. Агент обязан без дополнительного напоминания предпринять сборку, безопасное развёртывание и live-проверку после каждой принятой задачи, включая UI и документацию. Это зона ответственности исполнителя задачи, даже если её код уже слит другим интегратором.
- Если основной `develop` отстаёт, содержит чужой WIP или занят другим агентом, **не использовать его как повод откладывать запуск**: найти либо создать отдельный чистый deployment-клон, получить актуальный `origin/develop`, удостовериться в ветке и совпадении SHA и собирать только его. Не выполнять `reset --hard`, `stash`, `clean` и не изменять чужие файлы.
- Если launcher сообщает «unknown service/another checkout» или порт занят, агент самостоятельно проводит **только чтение** HTTP `/internal/rewrite-status`, проверку PID, командной строки, WSL-процесса и его рабочего каталога, чтобы определить владельца. Не считать одно сообщение launcher достаточным доказательством невозможности развёртывания. **Не останавливать чужой или неидентифицированный процесс** и не менять его файлы; при подтверждённой своей Studio использовать штатный guarded restart после проверки `shutdown_safe=true` и отсутствия активных заданий.
- Сначала собрать и проверить кандидата; только затем безопасно переключать подтверждённую Studio. После запуска сверить точный SHA `origin/develop` с live HTML и проверить затронутый сценарий; при необходимости исправить сбой запуска в рамках задачи и повторить безопасную проверку. Если действительно невозможно — зафиксировать диагностику, конкретный блокер и «Не завершено», не выдавать публикацию коммита за применённый результат. Не просить пользователя выполнить штатное обновление вручную.
## 4. Формат ответа и уборка

- **Только после live HTTP-проверки и обязательного удаления своих завершённых веток/worktree** ответ начинается с **«Выполнил»**, содержит краткое изменение, точный commit SHA, проверки и **ссылку на запущенную Studio, собранную именно на нём**. На HOME-PC: [http://127.0.0.1:8875/studio](http://127.0.0.1:8875/studio). Ссылка локальная для компьютера с Studio. Ссылку на GitHub commit можно приложить отдельно; она не заменяет ссылку на приложение.
- **Обязательное завершение каждого агента:** после успешной интеграции, push и проверенного развёртывания **удалить свою рабочую task-ветку и её worktree**, а интегратору — также свою временную интеграционную ветку и worktree. Сначала подтвердить чистоту worktree, отсутствие процессов и включение всех коммитов задачи в `origin/develop` (либо документированную эквивалентность при cherry-pick); затем штатный `git worktree remove <path>` без `--force` и `git branch -d <branch>`. Убедиться через `git branch --list` и `git worktree list`, что они действительно удалены. Если Git не позволяет удалить ветку, задачу **не называть выполненной**: указать блокировку. Публичную task-ветку удалять только после проверки эквивалентности и отсутствия чужого владельца. Не удалять чужие или незавершённые ветки и worktree.
- Перед слиянием оставшихся старых веток проверять ancestry, `git log --cherry-pick`/patch-id и фактический код: cherry-pick может уже содержаться в `develop` с **другим SHA**. Отсутствие ancestry не доказательство незавершённой задачи.
- Запись в `docs/RUST_MIGRATION.md` готовится **до** итогового коммита; отдельный документационный commit **после развёртывания** вновь сдвинет `develop` и сделает SHA запущенной сборки устаревшим. Фактический статус запуска зафиксировать в ответе.

Порядок: task-ветка → тесты → commit → последовательная интеграция → тесты объединённого дерева → push `develop` → release build от опубликованного SHA → безопасный restart → HTTP/commit/scenario PASS → «Выполнил» + ссылка.
