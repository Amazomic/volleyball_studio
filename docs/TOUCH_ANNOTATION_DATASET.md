# Дообучение: сравнение розыгрышей по траектории и ручной эталон

## Поток данных и границы ответственности

1. Первичный GPU-анализ сохраняет наблюдения мяча VBallNet и игроков/RTMPose.
2. CPU replay `native_cpu_replays/<replay_id>/tracked_frames.jsonl` хранит выбранный мяч с SHA-256.
3. Детектор `cpu_retrack/ball_track.rs::preliminary_rally_scope` находит перегибы «вниз → вверх» **только по мячу**, независимо от назначения игроку/типа удара. CPU Touch записывает `native_cpu_touch_runs/<touch_id>/preliminary_rallies.json` с `trajectory_impacts`, `rally_intervals`, параметрами и контрольной суммой в манифесте.
4. Основная CPU-постобработка использует предварительные границы для ограничения анализа и отдельно формирует подтверждённые позой/движением кандидаты касаний и временную разметку розыгрышей. Исходные GPU/CPU снимки неизменяемы.
5. Вкладки «Просмотр» и «Дообучение» используют один выбранный `project_id + rally_run_id + video` и один временной ряд. API `GET /api/training/rally-comparison` через `inspect_project` проверяет цепочку CPU/Touch и SHA-256 сохранённых перегибов, затем в памяти пересчитывает интервалы по выбранным параметрам; CPU-версию не перезаписывает.
6. `GET/POST /api/training/annotations` работает с самостоятельным эталоном. Сохранённые исправления не становятся предсказаниями детектора. `reviewed=true` разрешает вывод метрик против эталона; черновик не считается проверенной точностью.

В старой CPU-версии без `preliminary_rallies.json` кнопка моделирования запускает **read-only** пересчёт перегибов из сохранённого `native_cpu_replays/<replay_id>/tracked_frames.jsonl` после проверки SHA-256. Повторный GPU-анализ и пересоздание CPU-версии не нужны; результаты не записываются поверх оригинала.

## Работа во вкладке «Дообучение»

Выберите проект, видео и сохранённую CPU-постобработку. Сверху показаны количество розыгрышей обоих способов, однозначные совпадения при IoU ≥ 0,5, пропуски/лишние интервалы и F1. Измените число перегибов (1–10), запас до/после (0–180 кадров), минимальную длину (15–900 кадров), максимальную паузу между перегибами (90–120 кадров), затем нажмите **«Смоделировать розыгрыши и касания»** над видео. Кнопка выводит интервалы и кандидаты касаний из сохранённой траектории с выбранными параметрами; они не равны подтверждённым действиям игрока. Применение параметров только экспериментальное и не меняет CPU-анализ.

На **единой** шкале под видео: CPU-розыгрыши — синеватые, интервалы по мячу — оранжевые, эталонные метки — зелёные, точки перегибов — светло-оранжевые, смоделированные кандидаты касаний после нажатия кнопки — ярко-жёлтые. Фильтр «Проверка расхождений» показывает пропущенные обоими способами кандидаты, несогласные границы и совпадения. Нажатие на элемент переводит исходное видео к спорному эпизоду.

Редактирование выполняется кликом по метке общей шкалы или по видео на паузе. Открывается меню добавления, сдвига/удаления касания и изменения границ розыгрыша. Теперь правки остаются локальным черновиком и не сохраняются автоматически: нажмите «Сохранить данные касаний», чтобы записать их атомарно с проверкой ревизии. После сохранения повторно нажмите «Рассчитать касания по мячу», чтобы подобрать порог/сдвиг на сохранённых примерах. Отдельное «Завершить проверку видео» подтверждает эталон. Прежние сохранённые метки не удаляются.

Кнопка **«Рассчитать касания по мячу»** сначала определяет розыгрыши по выбранному алгоритму мяча (устойчивая траектория или перегибы) и его текущим настройкам, затем объединяет соседние интервалы при паузе менее значения из шапки списка (по умолчанию 4 с). Только в полученных интервалах выполняется поиск первичных кандидатов касаний по сохранённым наблюдениям VBallNet. Вне них ничего не ищется и не возвращается; если розыгрышей нет, результат пустой, без подмены CPU-розыгрышами. У каждого кандидата только кадр и оценка уверенности — ни тип действия, ни игрок здесь не назначаются. Сервер самостоятельно проверяет исходную CPU/GPU-цепочку и пересчитывает интервалы, не доверяя клиентским границам. При смене настроек розыгрышей старый прогноз сбрасывается. Отдельный повторный GPU-инференс не требуется.

## Две цели сохранённых данных

- `<data_root>/training/touch_annotations.json` — версия 1 эталона: кадры касаний, начала/концы розыгрышей, ревизии, источник и подтверждение. Используется для проверки кастомного детектора касаний/розыгрышей и как размеченный источник данных для будущего обучения TCN.
- `<data_root>/training/examples.json` — версия 1 библиотеки RTMPose: подтверждённые человеческие касания, точки тела, признаки движения и разметка площадки. Эта библиотека влияет на **следующий CPU-анализ** алгоритма, а не заменяет эталонные временные метки.
- `preliminary_rallies.json` — независимые предварительные интервалы и перегибы мяча, вычисленные до ручного подтверждения. При изменении порогов расчёт выполняется из сохранённых перегибов без запуска GPU.

Текущие веса Volley3D TCN **не дообучаются** по кнопке сохранения и вкладка не утверждает, что модель переобучена. Для реального обучения потребуется отдельный версионированный датасет последовательностей VBallNet с ручными метками, делением по исходным видео на train/validation/test и отдельным запуском тренировки. F1 сравнения CPU с детектором мяча не является независимой оценкой качества: предварительная траектория уже участвует в CPU-пайплайне; ориентир качества — сравнение с подтверждённым ручным эталоном.

## Калибровка касаний по траектории VBallNet — перенос старой ветки

В режиме «Дообучение» работают два отдельных расчёта. «Смоделировать розыгрыши и касания» использует существующее сравнение CPU-разметки и интервалов мяча. Новая кнопка «Рассчитать касания по мячу» запускает POST /api/training/trajectory/calculate: по всей записи ищет scored-кандидаты перегибов из сохранённого CPU replay, проверяя SHA-256, и не запускает GPU/RTMPose повторно.

Рабочий цикл:
1. Выберите проект, видео и CPU-постобработку. Нажмите «Рассчитать касания по мячу». На единой шкале под видео появятся жёлтые прогнозные маркеры, не являющиеся подтверждёнными касаниями.
2. «Взять расчёт для правок» переносит прогноз в локальный черновик с зелёными маркерами. Также можно использовать CPU-метки в качестве основы. Маркеры и границы розыгрышей выбираются левым кликом и меняются перетаскиванием или через контекстное меню по правому клику; удаление и смещение выполняются явно. Переключатель метода включает траекторию VBallNet или точки RTMPose; фильтр скрывает лишние слои.
3. Пока черновик изменён, повторный расчёт блокирован. «Сохранить данные касаний» выполняет POST /api/training/annotations с action=save, revision, UUID, touches и rallies. Rust проверяет исходник, CPU-версию, уникальность и диапазоны кадров и сохраняет в training/touch_annotations.json независимо от CPU/GPU evidence. Одновременно кеширует признаки scored-кандидатов и SHA CPU replay.
4. Повторное нажатие «Рассчитать касания по мячу» подбирает порог score и сдвиг −2…+2 кадра по сохранённым примерам, в том числе по отрицательным примерам без касаний. Отображаемая точность — только на обучающих видео, не независимая валидация. Уже подтверждённые разметки из прежней версии без нового кеша автоматически участвуют в калибровке текущего видео через временно вычисленные scored-кандидаты. Этот путь ничего не сохраняет и не снимает статус подтверждения; явное сохранение новых правок по-прежнему обязательно.
5. «Завершить проверку видео» подтверждает сохранённый эталон отдельно от сохранения черновика. Веса TCN/RTMPose при этих действиях не обновляются; GPU и исходные CPU-результаты не перезаписываются.

Канонический motion-детектор: rust/volley-core/src/motion/trajectory.rs. Полный SHA-проверяемый scan: rust/volley-app/src/native_player_tracks/trajectory.rs. Подбор профиля и read-only API: rust/volley-app/src/touch_annotation/trajectory.rs. Сохранение: rust/volley-app/src/touch_annotation.rs. UI: rust/volley-app/static/studio.js, studio.html, studio.css. Сравнение временных границ розыгрышей остаётся в rust/volley-app/src/rally_training_comparison.rs.

Проверки включают синтетический полный replay с неверным SHA, совместимость старой JSON-схемы меток, калибровку порога/сдвига на позитивном и негативном примерах и интерактивный Node-тест цепочки Calculate → Adopt → Edit → Save → Recalculate. Реальные видео, точность на независимом матче и GPU требуют отдельной проверки.

## Экспериментальный детектор непрерывной траектории

В «Дообучении» выбирается один из двух алгоритмов: «Устойчивая траектория мяча» (по умолчанию) либо «Перегибы траектории». Показываются настройки только выбранного режима, а параметры второго не попадают в запрос. Старые четыре параметра и подбор по эталону доступны только в режиме перегибов.

Режим «Устойчивая траектория мяча» (`coherent_vballnet_motion_v2`) читает SHA-проверенный `native_cpu_replays/<replay_id>/tracked_frames.jsonl` и анализирует **реальное перемещение центра выбранного мяча**, а не только наличие VBallNet-бокса. Трёхкадровые медианы сравниваются с разносом 16 кадров; движение учитывается при нормализованном смещении от 0,025 до 0,3. Неподвижный ложный объект отбрасывается, короткие пропуски свидетельств движения до 24 кадров объединяются, а фрагмент должен содержать свидетельство движения не менее чем на 35% кадров. Длительность принимается строго больше `min_trajectory_seconds` (по умолчанию 3,0 с, диапазон 0,1–120 с) на шкале 30 FPS.

Кнопка «Рассчитать касания по мячу» выполняет независимый расчёт *кандидатов касаний* и одновременно обновляет в «Дообучении» *альтернативные розыгрыши* на той же временной шкале. «Взять расчёт для правок» переносит рассчитанные границы в черновик, когда существующих ручных розыгрышей нет; при наличии ручных границ они сохраняются. Алгоритм не подтверждает касания игроков и не назначает им типы или личности. Предварительные розыгрыши не подменяют опубликованную CPU-постобработку; GPU, replay, оригинал и ручной эталон не перезаписываются.

Проверка на сохранённом размеченном видео проекта «новый» (1737 кадров): прежний детектор с порогом 3,0 с создавал шесть разрозненных фрагментов; новый Rust-детектор создаёт интервалы `[153,763]` и `[912,1440]` против подтверждённых `[153,725]` и `[895,1425]`. Совпали 2/2 розыгрыша при IoU ≥ 0,5; индивидуальные IoU 93,8% и 94,1%, суммарный IoU 93,9%. Среднее абсолютное отклонение границ — 0,58 с. Это **in-sample**-проверка после подбора констант на данном видео; независимая точность на других матчах не измерена.

## Управление слоями и контекстными действиями в «Дообучении»

В заголовке «Списка розыгрышей» доступны два независимых чекбокса: «Розыгрыши по касаниям» (текущая сохранённая CPU-постобработка) и «Розыгрыши по траектории мяча» (альтернативный результат моделирования). Оба одновременно управляют карточками списка и соответствующими слоями на единой шкале; ничего не пересчитывают и не сохраняют. Полупрозрачные бирюзовые и янтарные интервалы нанесены на одну координатную шкалу, поэтому пересечения различимы; при выключении слоя по касаниям скрываются также зелёные интервалы ручного эталона, подтверждённые CPU-касания и интерактивные метки ручных касаний на шкале. При выключении слоя мяча скрываются также прогнозные жёлтые метки кандидатов касания и метки перегибов. Сохранённые данные и списки разметки не удаляются. Второй слой появляется при наличии результата расчёта по мячу. В обычном предпросмотре управление остаётся прежним.

Левый клик по плееру, метке, строке или шкале не открывает редактор касания: он выбирает объект или перемещает курсор. Меню добавления, перемещения и удаления касаний или границ розыгрышей вызывается правой кнопкой мыши в режиме ручной разметки; для клавиатуры доступны ContextMenu и Shift+F10. Предварительные и подтверждённые данные не изменяются до явного выбора действия и сохранения.

Проверки: `scripts/ci/test_training_rally_layers.mjs`, `scripts/ci/test_training_context_actions.mjs`, `scripts/ci/test_training_workspace.mjs`. Легенда общей шкалы отображает цвет каждого включённого слоя.

## Единый фильтр списка и шкалы в «Дообучении»

Чекбоксы «Розыгрыши по касаниям» (бирюзовый) и «Розыгрыши по траектории мяча» (янтарный) находятся в заголовке правого «Списка розыгрышей», а не поверх видеоплеера. Это единственные переключатели источников для списка и общей шкалы. Их выключение скрывает карточки соответствующего источника и его цветные интервалы/маркеры; переключение не изменяет сохранённые CPU-данные, ручной эталон или результат моделирования.

В режиме «Дообучение» оба источника показываются в общем списке в хронологическом порядке. CPU-карточки сохраняют исходный ID, статистику касаний, привязки и избранное. Карточки по траектории содержат только подтверждённые алгоритмом границы и длительность; они явно помечены как предварительные, без назначения игроков и касаний и без возможности записать их в CPU-избранное. Клик выбирает временной интервал для просмотра. При выходе из «Дообучения» возвращается прежний CPU-список и исходная сортировка/фильтр. Повторный CPU/GPU-анализ не запускается.

Регрессии: `scripts/ci/test_studio_rally_cards.mjs`, `scripts/ci/test_training_rally_layers.mjs`, `scripts/ci/test_training_rally_comparison.mjs`.

## Совпадение начала розыгрыша и маркера воспроизведения

При нажатии на карточку розыгрыша, её мини-шкалу, при последовательном воспроизведении и на общей шкале используется одна пара обнаруженных границ: `detected_start_frame`/`detected_end_frame` для CPU и `start_frame`/`end_frame` для индекса, а у рассчитанных по мячу интервалов — `start`/`end`. Начало позиции воспроизведения совпадает с отмеченным началом розыгрыша, а полоса прогресса карточки рассчитывается относительно того же интервала. Перерисовка указателя происходит после назначения `video.currentTime`, поэтому предыдущая позиция не отображается как новая.

`manual_clip.start_frame/end_frame` — отдельные границы **монтажного экспорта** с запасом кадров; они остаются неизменными и не сдвигают предпросмотр. Например, в сохранённом CPU-результате проекта с двухчасовым видео розыгрыш `c73b8a` начинается по детектору с кадра 174 (5,8 с), тогда как подготовленный монтажный клип начинается с кадра 129 (4,3 с). Предпросмотр теперь открывается на кадре 174, совпадая с зелёной/бирюзовой отметкой на общей шкале. Регрессии: `scripts/ci/test_studio_rally_card_progress.mjs` и `test_studio_rally_cards.mjs`.

## Полная ширина шкалы в «Дообучении»

Одна общая временная шкала `#studio-timeline` остаётся дочерним элементом сетки `#studio-preview-view .viewer-layout` во всех режимах; её место — отдельная строка `grid-area: timeline`, `grid-column: 1 / -1` под плеером и правым списком розыгрышей. В режиме «Дообучение» шкала больше не переносится внутрь узкой `viewer-panel`; она растягивается до правого края рабочей области, как в «Предпросмотре», без отдельного скроллбара, дублирования шкалы или пересоздания меток. Блок настроек/редактирования разметки переносится в следующую общую строку сетки (`training`), поэтому шкала остаётся **сразу под видео**, а не ниже длинного редактора. При выходе из дообучения блок настроек возвращается в исходную панель. На экранах шириной до 780 px порядок: видео → шкала → список → редактор. После переключения режима размеры Canvas обновляются через `requestAnimationFrame(drawTimeline)`. Проверка: `scripts/ci/test_training_workspace.mjs`.

## Экспериментальное объединение розыгрышей и происхождение касаний

Только вкладка «Дообучение». Параметр «Объединять при паузе меньше» по умолчанию 4 секунды. Группировка выполняется отдельно для сохранённых CPU-розыгрышей «По касаниям» и для рассчитанных «По траектории мяча». Если расстояние между концом одного интервала и началом следующего строго меньше заданного числа секунд с учётом FPS, интервалы показываются одним отрезком. Пересекающиеся и смежные интервалы объединяются всегда; пауза ровно 4 секунды при пороге 4 секунды не объединяется. Длительность объединённого интервала включает поглощённые короткие паузы. Сводка для каждого расчёта показывает уже объединённое количество и суммарное время независимо от видимости слоя.

Для CPU группировка использует полный проверенный Rust-индекс /api/cpu/native/rallies/timeline, а не страницу загруженных карточек; до получения индекса временно используются загруженные карточки. Для мяча используются только trajectory_rallies при trajectory_status=ready. Одинаковые интервалы выводятся в карточках и на общей шкале и применяются при выборе позиции на ней. Метрики IoU/F1 углублённого сравнения относятся к исходным (не объединённым) результатам. Синтетические объединённые карточки не получают придуманных касаний, игроков и избранного. В обычном «Предпросмотре» исходные CPU-границы, экспорт и постобработка неизменны.

Источники меток касаний разделены: 1) CPU — только обычный предпросмотр выбранной постобработки; 2) зелёные — ручная разметка дообучения; 3) жёлтые — неподтверждённые кандидаты отдельного алгоритма по мячу в дообучении. Жёлтые кандидаты берутся только из /api/training/trajectory/calculate (VBallNet) и показываются по отдельному чекбоксу «Определение касания», по умолчанию выключенному. Обобщённые trajectory_impacts — повороты траектории без подтверждения касания игрока — больше не выдаются за метки касаний. Режим continuous определяет только интервалы розыгрышей; возможные касания получает дополнительная, отдельно включаемая функция расчёта. Ни один кандидат не становится подтверждённым касанием без явного сохранения разметки.

Регрессии: scripts/ci/test_training_merge_preview.mjs, test_training_rally_layers.mjs, test_studio_rally_cards.mjs, test_training_rally_comparison.mjs.


## Изоляция касаний по мячу в дообучении (2026-11-21)

В режиме «Дообучение» слой «Определение касания» использует исключительно предложения API `/api/training/trajectory/calculate` из проверенной траектории VBallNet в границах розыгрышей по мячу. Архивные CPU `touch_annotations` не рисуются на видео, временной шкале и шкалах карточек; старое автозаполнение черновика CPU-метками недоступно. Кандидат — только кадр и оценка, а не подтверждённое касание игрока. Он выделяется на видео возле мяча, если доступна соответствующая координата сохранённого replay, иначе показывается сообщение о недоступной позиции. Вторая независимая настройка «Определение типа касания» показывает отсутствие типа, не копируя классы из CPU-постобработки. Автономный классификатор RTMPose для этих кандидатов ещё не подключён: этот переключатель не является готовой моделью определения типа. Ручной эталон остаётся отдельным редактируемым слоем. Проверки: `scripts/ci/test_training_rally_layers.mjs`, `scripts/ci/test_studio_touch_training_ui.mjs`.


## Три независимых этапа дообучения (2026-11-21)

Панель над видео содержит три последовательные операции: **«Рассчитать розыгрыши»** — границы только по непрерывной траектории VBallNet; **«Рассчитать касания»** — неподтверждённые кандидаты только внутри найденных розыгрышей; **«Определить тип касания»** — независимая классификация этих же кадров по исходным рамкам Track ID и RTMPose, без повторного GPU-инференса и без чтения готовых типов из CPU-постобработки. Третий этап использует отдельный эндпоинт POST `/api/training/trajectory/types` с жёсткой проверкой SHA replay, версии кандидатов, интервалов и исходного GPU fusion. На экране и временной шкале цветом показываются только типы с достаточными признаками контакта и движения. Нераспознанные остаются «Касание»; результаты сохраняют статус гипотез, не подменяют ручную разметку. В данной версии поза распознаёт «Атака», «Передача сверху» и «Приём снизу»; «Подача» и «Блок» без подтверждённого контекста площадки остаются без типа. При отсутствующем RTMPose выводится явная ошибка источника. Проверьте реальные матчи отдельно; модуль не оценивает точность по эталону автоматически.
