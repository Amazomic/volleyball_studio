# Параллельная работа агентов: изоляция, алгоритмы и интеграция

Дата: 2026-11-14. Применяется вместе с [AGENTS.md](../AGENTS.md) и [чеклистом улучшений](AGENT_IMPROVEMENT_CHECKLIST.md).

Цель — параллельно улучшать анализ и персонализированный монтаж, исключая перезапись чужих файлов, смешивание результатов и вмешательство в работающую Studio. Независимые изменения объединяются только после проверки совместимости.

Это регламент и алгоритмы для агентов, а не установленный автоматический диспетчер или файловая песочница. Отдельные worktree изолируют рабочие файлы; логическую совместимость изменений обеспечивают договорённости об интерфейсах и интеграционные проверки. При отсутствии настоящей изоляции несколько агентов могут параллельно читать и анализировать, но изменять общую рабочую копию может только один исполнитель.

## 1. Правила, которые нельзя обходить

1. Один пишущий агент — один абсолютный путь worktree — одна отдельная ветка `codex/<run-id>/<task-id>`. Передавать агенту путь явно; наследуемый каталог не считать изолированным.
2. У каждой задачи есть фиксированный `base_sha`, перечень разрешённых изменений `write_paths`, потребляемые и изменяемые контракты, проверки и критерий готовности.
3. Две активные задачи не владеют одним изменяемым файлом, даже если собираются редактировать разные строки. Пересечение каталогов и создаваемых файлов тоже считается пересечением.
4. Общие точки входа, зависимости, схемы и документы интеграции изменяет один назначенный владелец. Новый владелец получает право только после явной передачи координатором.
5. Агент не пишет в worktree другого агента, общий checkout пользователя, общие данные Studio и соседние каталоги вывода. `git reset --hard`, `git clean`, массовый `restore`, общий `stash`, принудительный checkout и force-push не являются средствами разрешения конфликтов.
6. Агент не добавляет обходной адаптер или вторую реализацию, чтобы обойти зависимость от чужой задачи. Изменение контракта сначала согласуется и версионируется.
7. Готовность подтверждается конкретными commit SHA и результатами проверок. Сообщение «сделано» и отсутствие текстового Git-конфликта недостаточны.
8. Рабочую Studio обновляет только интегратор после проверки объединённого результата и активных заданий. Исполнители управляют только своими тестовыми экземплярами.

## 2. Роли и единый источник координации

| Роль | Ответственность | Ограничение |
| --- | --- | --- |
| Координатор | Делит работу, фиксирует базу, выдаёт владение файлами и ресурсами, ведёт зависимости и статусы | Один активный координатор на один запуск |
| Исполнитель | Реализует одну согласованную задачу в своём worktree, проверяет и передаёт коммиты | Не расширяет область записи самостоятельно |
| Интегратор | Последовательно принимает коммиты, меняет общие точки, проводит сквозные проверки и применяет результат | Единственный автор изменений интеграционной ветки |
| Ревьюер | Проверяет конкретный SHA и критерии задачи; сообщает замечания | Не редактирует проверяемую копию; исправления возвращает исполнителю |

Координатор и интегратор могут быть одним агентом. Число исполнителей ограничено доступными агентами, независимыми задачами и ресурсами машины. Роль не требует запуска дополнительного агента, если работа выполняется последовательно.

Координатор создаёт `docs/agent-runs/<run-id>/coordination.md` по [шаблону запуска](agents/RUN_TEMPLATE.md) в своей интеграционной копии. Это единственный актуальный реестр; его копии в ветках исполнителей являются снимками. Координатор один меняет назначения и увеличивает `revision`. Исполнитель получает подтверждённые `task_id`, `grant_epoch` и абсолютный путь реестра через доступный канал координации.

При изменении прав конкретной задачи координатор увеличивает её `grant_epoch`. Изменение статуса соседней задачи не отзывает остальные назначения. Markdown не даёт атомарной блокировки: единственный автор реестра и явное подтверждение выдачи прав обязательны. При смене координатора прежний должен прекратить координацию; новый сначала сверяет реальные процессы, SHA и незавершённые операции Git.

Статусы задачи: `planned → ready → running → review → accepted → integrated`. `blocked` означает известную зависимость или препятствие, `changes_requested` — возврат на исправление. `accepted` означает готовность переданного результата к интеграции, а `integrated` — успешные проверки уже в объединённой версии. Статус всего запуска `applied` ставится отдельно после применения в Studio, когда оно требуется.

## 3. Алгоритм A: разбиение задач и запуск независимой группы

Вход: цель пользователя, текущие владельцы из `RUST_CANONICAL_OWNERS.json`, исходный коммит и ограничения ресурсов.

1. Найти существующий путь функции от данных до результата. Разбивать работу по самостоятельным изменениям поведения, а не механически по числу агентов или строк кода.
2. Для каждой задачи заполнить [карточку](agents/TASK_TEMPLATE.md): `write_paths`, `read_paths`, `contracts_read`, `contracts_write`, `depends_on`, ресурсы, выходной результат и проверки.
3. Включить в `write_paths` тесты, создаваемые файлы, генераторы и отслеживаемые результаты генерации. Учесть переименования по старому и новому пути. Соседство модулей не даёт права на запись.
4. Построить граф зависимостей: ребро A → B означает, что B требует принятого контракта или результата A. Цикл устранить выделением общего контракта или объединением связанных задач.
5. Если меняются общие типы/API, сначала выполнить отдельную задачу контракта: типы, семантика, совместимость и проверки. Интегрировать её, назначить новый `base_sha`, затем запускать потребителей. Тестовая заглушка допустима только как часть явного теста и не заменяет реализацию в продукте.
6. Среди задач с интегрированными зависимостями выбрать непересекающуюся группу. Порядок: P0 → задачи, разблокирующие остальных → наибольший ожидаемый пользовательский эффект при разумном объёме проверки. Не дробить маленькую связанную правку ради параллельности.
7. Выдать worktree и ресурсы текущих фаз, получить подтверждение исполнителей, перевести задачи в `running`. Фазы без свободных ресурсов остаются в очереди; независимые правки и анализ могут выполняться параллельно, даже если обеим задачам позже понадобится одна GPU.

Конфликт между A и B существует, если пересекаются `write_paths`, они несовместимо изменяют/потребляют один контракт или их текущие фазы требуют одновременно один эксклюзивный ресурс. Пересечение `write_paths(A)` с `read_paths(B)` требует проверки семантики: B читает фиксированную базу, поэтому запись A физически ему не мешает, но может сделать его предположения устаревшими при интеграции. Такие зависимости явно записываются.

Пути сравнивать после нормализации разделителей, учёта нечувствительности Windows к регистру и разрешения родительских каталогов/ссылок. Проверять границы компонентов пути: `src/a` и `src/ab` не один каталог. Новому файлу нормализовать существующего родителя. Не использовать широкое `rust/**` вместо фактического перечня задачи.

```text
ready = задачи с принятыми контрактами и интегрированными зависимостями
selected = пустой набор
для task в ready по приоритету:
    если есть слот и нет конфликта с selected и активными назначениями:
        координатор резервирует task целиком
        добавить task в selected
запустить только задачи с подтверждённой выдачей прав
```

Пример для Volleyball Studio:

| Поток | Возможная изолированная задача | Граница |
| --- | --- | --- |
| Касания | Дедупликация физических контактов и её тесты в модуле-владельце | Не менять одновременно схему события и реконструкцию розыгрышей |
| Личность | Разрешение неоднозначных ReID-привязок и тесты | Не изменять общий selector или значения подтверждения без задачи контракта |
| Монтаж | Улучшение отбора на уже согласованных событиях и привязках | Зафиксировать входную схему, не вводить собственное определение личности |
| Интеграция | Регистрация API, общие UI-подключения, схемы, сквозной сценарий | Выполнять после приёмки необходимых потоков |

Это пример распределения, не готовые назначения: реальные файлы и пересечения определяются перед каждым запуском.

## 4. Алгоритм B: подготовка и проверка изоляции

1. В исходной копии прочитать `git status --short`, `git log -8 --oneline`, `git worktree list --porcelain`. Сохранить незавершённые пользовательские изменения на месте. Не коммитить и не переносить их автоматически.
2. Выбрать полный SHA базы. Worktree из HEAD содержит только коммит; незакоммиченная работа в него не попадает. Если задача зависит от неё, координатор получает согласованный коммит от владельца или откладывает зависимую часть.
3. Проверить уже предоставленную изоляцию через `git rev-parse --show-toplevel --git-dir --git-common-dir` и `git rev-parse --show-superproject-working-tree`. Не создавать вложенный worktree поверх уже выделенного; отличать worktree от submodule. Управляемый средой detached HEAD сохранять до штатного назначения ветки.
4. Использовать штатное средство worktree среды, если оно доступно. Иначе создать отдельные каталоги через Git в разрешённом месте. При отказе доступа не переводить нескольких писателей в общую копию: продолжать параллельное чтение или последовательное редактирование одним агентом.
5. Передать исполнителю абсолютный путь и проверить в нём SHA, ветку и чистоту. Все shell-команды выполнять с явным `workdir` либо `git -C`; все записи привязывать к назначенному корню.
6. Подготовить отдельные данные, сборочные выходы, временные файлы и при необходимости тестовый сервер. Не копировать пользовательский рабочий каталог целиком.

Пример резервного варианта в PowerShell после выбора разрешённого каталога и подтверждения базы; команды не запускаются самим чтением инструкции:

```powershell
$agentRepo = (git rev-parse --show-toplevel).Trim()
$agentBase = (git rev-parse HEAD).Trim()
$agentRun = '20261114-analysis-01'
$agentRoot = Join-Path (Split-Path -Parent $agentRepo) "volley-agents-$agentRun"
git -C $agentRepo worktree add -b "codex/$agentRun/integrate" (Join-Path $agentRoot 'integrate') $agentBase
git -C $agentRepo worktree add -b "codex/$agentRun/touch" (Join-Path $agentRoot 'touch') $agentBase
git -C $agentRepo worktree add -b "codex/$agentRun/identity" (Join-Path $agentRoot 'identity') $agentBase
```

Каждую команду выполнять отдельно и проверять код завершения; пример не является скриптом автоматического развёртывания. Не применять `-B`, `--force` или `--ignore-other-worktrees`. Каталоги не должны существовать заранее; если worktree размещаются внутри репозитория, координатор сначала проверяет их исключение из Git. Не использовать вложенный путь другой активной рабочей копии.

У worktree раздельные `HEAD` и index, но общие Git-объекты, refs и обычно конфигурация. Поэтому исполнители не меняют общие настройки Git, hooks, remote, чужие ветки и stash. `git worktree lock` защищает служебную запись от удаления/очистки, а не файлы от другого агента. Эти свойства описаны в [документации Git worktree](https://git-scm.com/docs/git-worktree/2.56.0).

### Изоляция ресурсов этого проекта

| Ресурс | Правило |
| --- | --- |
| `VOLLEY_RUST_DATA_ROOT` | Уникальный абсолютный WSL-путь на задачу вне репозитория; значение по умолчанию не использовать для параллельных тестовых серверов |
| Порт Studio | Координатор выделяет свободный localhost-порт; фактический bind подтверждает доступность. 8875 остаётся рабочей Studio |
| Бинарники и WASM | Собственный `rust/target` и `static/volley_web.wasm` внутри каждого worktree; не копировать артефакт из соседней ветки |
| `CARGO_TARGET_DIR` | Не направлять разные задачи в общий изменяемый target. Launcher сейчас ожидает `<worktree>/rust/target/release/volley-app`; внешнее значение требует отдельной проверки пути запуска |
| Временные файлы и отчёты | Уникальные каталоги по `run_id/task_id`, включая FFmpeg-временные файлы и отчёты бенчмарка |
| Веса и исходные свидетельства | Общие только для чтения с проверкой версии/SHA; экспериментальные веса, оптимизированные графы и изменяемые provider-кэши — отдельные |
| GPU, кодировщик, тяжёлые CPU-сборки | Учёт фаз и ресурсов по алгоритму E; сравнение скорости не выполнять одновременно с конкурирующей нагрузкой |
| Пользовательские проекты, результаты и фото | Не использовать для изменяющих тестов. Нужные фикстуры готовить отдельно без изменения оригинала |

Worktree не переносит игнорируемые модели, WASM и локальные зависимости автоматически. Их наличие и способ подготовки проверить до теста. Общий каталог загрузок Cargo допустим при штатных блокировках Cargo; агенты не выполняют его очистку или изменение общего toolchain.

Для тестовой Studio использовать launcher из своего worktree, явные `-Bind` и `-DataRoot`. `DataRoot` принимает абсолютный WSL-путь, а не Windows-путь. Пример после выдачи ресурсов:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File 'C:\approved\volley-agents\touch\scripts\start-volley-rust-dev.ps1' -Action Start -Bind '127.0.0.1:18876' -DataRoot '/tmp/volley-agents/20261114-analysis-01/touch/data'
```

Пути в примере заменить назначенными. Для `Status`, `Stop` и `Restart` передавать тот же worktree, порт и DataRoot. Свободный другой порт не разрешает второй сервер из того же checkout: [runtime](../rust/volley-app/src/runtime.rs) блокирует экземпляр по корню репозитория. Проверять принадлежность процесса; не завершать чужой сервер.

## 5. Алгоритм C: выдача прав и изменение области задачи

1. Исполнитель отправляет координатору список нужных файлов, контрактов и ресурсов. До подтверждения выполняет только чтение.
2. Координатор проверяет пересечения со всеми активными назначениями, включая `review` и `accepted`, и регистрирует задачу с новым `grant_epoch`. Владение сохраняется до интеграции или явной передачи.
3. Исполнитель подтверждает полученные epoch, путь, base SHA и список записи. Перед началом новой серии правок и после возобновления прерванной работы сверяет, что назначение не отозвано.
4. При необходимости нового файла, зависимости или изменения контракта исполнитель приостанавливает зависимую запись, сообщает причину и продолжает только независимую разрешённую работу. Координатор расширяет назначение или выделяет отдельную задачу.
5. Пропавший ответ или истёкшее время не освобождают владение. Перед передачей координатор подтверждает остановку прежнего исполнителя и его процессов, сохраняет SHA и незакоммиченный результат, затем увеличивает epoch. Если остановка не подтверждена, конкурентную запись не выдавать.
6. Результат со старым epoch не интегрировать автоматически; сначала сверить фактические изменения с новым владельцем. Потеря координатора не означает разрешение самоназначения: сохранить работу и запросить восстановление координации.

## 6. Алгоритм D: локальный цикл и раннее обнаружение конфликта

1. Прочитать карточку, канонического владельца, затронутые схемы и ближайшие тесты. Искать через `rg` по выбранным путям; расширять поиск, если зависимость выходит за них.
2. Воспроизвести проблему или исходный сценарий. Зафиксировать имеющиеся сбои. Выполнить минимальное связное изменение поведения в разрешённых файлах.
3. После серии правок проверить полный набор изменений: коммиты относительно `base_sha`, unstaged, staged и untracked. Один `git diff` не показывает все эти категории.
4. Для любого пути вне `write_paths` остановить передачу результата и выяснить происхождение. Не удалять и не откатывать неожиданную правку: она может принадлежать другому процессу или генератору.
5. Запустить целевую регрессию, затем проверки затронутых контрактов. Форматирование выполнять только в своей копии; если `cargo fmt --all` меняет посторонние модули, эти изменения не считать автоматически разрешёнными.
6. Проверить staged diff, добавить только явные пути, сделать короткий русский коммит. Не применять `git add .` или `git add -A` как способ собрать неизвестное содержимое.
7. Передать точные SHA, отчёт и запрос интеграции. После `review` не изменять переданный результат незаметно: исправление создаёт новый коммит и новую заявку на проверку.

Команды аудита из своего worktree; `$agentBase` — полный SHA из карточки:

```powershell
git diff --name-status --no-renames $agentBase HEAD
git diff --name-status --no-renames
git diff --cached --name-status --no-renames
git ls-files --others --exclude-standard
git diff --check
git diff --cached --check
```

Проверка путей выполняется также при приёмке коммитов. Игнорируемые build/data-файлы в этот список не входят: их расположение сверять с выделенными каталогами ресурсов. Файловый аудит не обнаруживает изменение поведения сам по себе — для этого нужны тесты и ревью контракта.

## 7. Алгоритм E: ограничение ресурсов без лишнего ожидания

1. Разбить выполнение на фазы: чтение/код → лёгкие тесты → сборка → GPU/медиа → передача. Ресурс запрашивать на фазу, а не удерживать на всё время работы агента.
2. Координатор учитывает доступные CPU/RAM/VRAM и активные пользовательские задания. По умолчанию выделяет одну тяжёлую GPU-фазу на устройство; дополнительную конкурентность разрешает только после измерения ресурсов.
3. В начале фазы выдать весь необходимый набор ограниченных ресурсов сразу либо поставить фазу в очередь. Не удерживать GPU в ожидании другого занятого ресурса: это устраняет циклическое ожидание.
4. Пока фаза ожидает ресурс, исполнитель завершает документацию, анализ или тесты, не требующие его. Не запускает повторно тот же долгий job из-за отсутствия быстрого ответа.
5. Измерения скорости проводить без конкурирующих сборок, инференса и кодирования на той же машине. Записывать фактическую постороннюю нагрузку; несопоставимый прогон не считать доказательством ускорения.
6. Освобождать ресурсы после подтверждённого завершения процесса и его дочерних задач. Ошибка агента или таймаут сообщения не доказывают освобождение GPU. Применять только штатную отмену своего задания.

## 8. Алгоритм F: контекст и проверки по области влияния

1. Координатор передаёт компактный пакет: цель, base SHA, карточка, владельцы и связанные пути, утверждённые контракты, исходные ошибки и критерий приёмки. Не пересказывать всю историю проекта каждой задаче.
2. Исполнитель проверяет пакет по текущим исходникам, затем читает только требуемые зависимости. Повторно использовать установленные факты можно вместе с SHA; изменившийся файл требует новой проверки относящихся к нему выводов.
3. Построить область влияния: изменённый модуль → его вызывающие модули → сериализация/кэши → API/UI → статистика/монтаж. Для каждого затронутого перехода выбрать проверку; при неизвестных зависимостях расширить набор.
4. Сначала запускать быстрый тест конкретного дефекта и проверки совместимости, затем обязательные проверки проекта. Это сокращает время до обнаружения ошибки, но не отменяет полный набор перед приёмкой интеграции.
5. Повторять тест, если изменились проверяемый код, транзитивные зависимости, fixtures, параметры, окружение или объединённый SHA. Старый зелёный результат сохранять только как историческое свидетельство, а не как PASS нового дерева.
6. Предварительные результаты передавать при изменении состояния: найденная причина, новый контракт, блокер, готовые коммиты. Не опрашивать соседних агентов непрерывно; использовать доступные уведомления и ожидание, пока выполняется независимая работа.

Минимум интегратора для изменений кода: `cargo fmt --all -- --check`, `cargo check --workspace --offline`, `cargo test --workspace --offline` из `rust/`; из корня — `node scripts/ci/test_volley_web_wasm.mjs`, `node scripts/ci/check_rust_ownership.mjs --self-test`, `node scripts/ci/check_rust_roadmap.mjs --check --self-test`. Подготовить WASM из текущего дерева до его проверки. Нативные GPU-тесты, размеченные матчи и экспорт проверяются отдельно по затронутому поведению; пропуск явно фиксируется.

## 9. Алгоритм G: последовательная интеграция

1. Исполнитель заполняет раздел передачи в своей карточке и предоставляет упорядоченный список собственных коммитов. Карточка хранится по уникальному пути `docs/agent-runs/<run-id>/tasks/<task-id>.md`; общий журнал исполнители не редактируют.
2. Интегратор проверяет epoch, base SHA, ancestry, фактические пути каждого коммита, контракты, результаты тестов и отсутствие посторонних изменений. Коммиты зависимостей не включать повторно; сравнение только имени ветки недостаточно.
3. В чистом интеграционном worktree записать текущий `integration_head`. Применить коммиты одной задачи в согласованном порядке через `git cherry-pick <sha>`. Интеграционные задачи выполняются по графу зависимостей; два cherry-pick/merge в этой копии одновременно запрещены.
4. При конфликте остановиться. Не выбирать массово `ours`/`theirs`. Сопоставить исходное требование, обе реализации и контракт; согласовать исправление с владельцем, выполнить регрессию. Если разрешение откладывается, использовать `git cherry-pick --abort` только для своей текущей операции; уже успешно принятые предыдущие операции сохранить и отразить в реестре.
5. После применения проверить смысловую совместимость, даже если Git не сообщил конфликт: единицы времени, поля и значения схем, смысл `unknown`, статусы подтверждения личности, cache keys, порядок событий и потребителей.
6. Интегратор выполняет свою часть подключения общих файлов и переносит принятую запись в `RUST_MIGRATION.md`; актуализирует ownership/roadmap только по фактическим изменениям. Для параллельного рабочего коммита роль записи в журнале выполняет индивидуальная карточка; при интеграции общий журнал обязателен.
7. Проверить объединённый результат. При сбое определить первый нарушенный контракт/коммит и вернуть конкретную задачу на исправление. До успешной проверки не ставить `integrated`; зависимые интеграции приостановить.
8. Записать соответствие исходных и интеграционных SHA, команды и результаты. Перед финальной проверкой закончить все изменения исходников и конфигурации; результат тестов относится к зафиксированному дереву. После любых последующих значимых правок повторить затронутые проверки.
9. Перед обновлением общей ветки убедиться, что её HEAD не изменился с согласованной базы, checkout свободен от чужих правок и есть исключительное право интеграции. Если ветка продвинулась, собрать и проверить новый кандидат на актуальной базе; не делать force-update. Грязную пользовательскую копию не очищать ради применения — сохранить проверенный результат в интеграционной ветке и указать, что препятствует переносу.
10. Применить итог в Studio один раз штатным launcher после проверки активных заданий. Отдельно сообщить «интегрировано» и «применено», если перезапуск безопасно отложен.

Cherry-pick переносит изменения выбранного коммита и требует чистого рабочего дерева; при конфликте есть штатные `--continue` и `--abort`. См. [Git cherry-pick](https://git-scm.com/docs/git-cherry-pick). Команды интеграции выполняются только в назначенной копии, не в текущем checkout пользователя по умолчанию.

### Общие файлы: один владелец на запуск

По умолчанию интегратору принадлежат `AGENTS.md`, README, `docs/RUST_MIGRATION.md`, `docs/RUST_CANONICAL_OWNERS.json`, `docs/RUST_ROADMAP.json` и генерируемая карта, `rust/Cargo.toml`, `rust/Cargo.lock`, общие Cargo manifests, `rust/volley-app/src/main.rs`, корневые `lib.rs`, общие схемы и подключения UI. Это не запрет менять их: нужная правка становится отдельной задачей владельца. При явной передаче файла исполнителю интегратор также не редактирует его до возврата владения.

Не дублировать регистрацию модулей, определения типов и обработчики «временно». Если изолированная задача не может компилироваться без изменения общего входа, сначала подготовить и интегрировать этот вход как часть контракта либо передать задачу целиком одному исполнителю.

## 10. Восстановление и завершение

- При непредвиденной записи в чужой путь остановить запись, сохранить diff и сообщить координатору. Восстановление выполняет владелец после сравнения, а не обнаруживший проблему агент вслепую.
- После перезапуска агента прочитать карточку, актуальное назначение и Git status; сверить последний принятый SHA. Не считать отправленный ранее запрос уже интегрированным.
- Не переписывать принятые коммиты. Неудачное интегрированное изменение исправлять новым коммитом; при необходимости отката проверить зависимые задачи и подготовить отдельный revert в интеграционной копии.
- Не переиспользовать `run_id/task_id`, порт или DataRoot незавершённой задачи. Истёкший срок без проверки процессов не делает ресурс свободным.
- Удалять worktree только после сохранения коммитов/отчётов, при отсутствии своих активных процессов и незакоммиченных файлов, штатным `git worktree remove` без `--force`. Проверить абсолютный путь; данные и ветки не удалять автоматически вместе с завершением чата.
- Итоговый отчёт: принятые задачи и SHA, общий результат проверок, реальные метрики качества/скорости, непройденные проверки, состояние Studio и оставшиеся зависимости.
