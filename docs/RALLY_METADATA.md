# Контракт метаданных розыгрыша (RallyMetadata v1)

Статус: проект контракта, не реализован в runtime. База проверки: df5619144d1f19f9a7bb4a92391ac61d4f4355e0. Цель: формировать один версионированный результат в ходе анализа, а не независимо вычислять состав и счёт в интерфейсе, отчёте и монтаже.

## Владельцы и хранение

- Сбор и сохранение: [cpu_rallies.rs](../rust/volley-app/src/cpu_rallies.rs), обе ветви (primary GPU mask и CPU reconstruction).
- Правила состава и результата: [rally_reconstruction.rs](../rust/volley-core/src/rally_reconstruction.rs); контекст подачи и типов: [rally_contact_context.rs](../rust/volley-core/src/rally_contact_context.rs).
- Проверка и выдача: [native_rally_evidence.rs](../rust/volley-app/src/native_rally_evidence.rs), [native_rally_preview.rs](../rust/volley-app/src/native_rally_preview.rs).
- Идентификация: [native_player_tracks.rs](../rust/volley-app/src/native_player_tracks.rs) и [player_identity.rs](../rust/volley-app/src/player_identity.rs).
- Предлагаемое размещение: поле `metadata` каждой записи `projects/<project_id>/native_cpu_rallies/<rally_run_id>/rally_candidates.jsonl`; версия схемы и политика расчёта в manifest.json. Не создавать независимый источник касаний. Изменение схемы требует новой версии CPU-результата; прежние артефакты не переписывать. Player ID и ручные подтверждения разрешать поверх снимка с ревизией привязок; не мутировать исходные Track ID и SHA. Промежуточные результаты доступны по этапам, публикуются атомарно по существующим правилам; отменённый анализ не заменяет принятый снимок.

## Целевая схема

Пример синтетический, не результат анализа реального матча. team_1/team_2 — стабильные ключи команд в матче; near/far — текущие половины, не идентификаторы команд.

```json
{
  "schema_version": 1,
  "rally_id": "candidate-id",
  "start_frame": 300,
  "end_frame": 540,
  "team_1": {"team_id": "team_1", "side": "near", "track_ids": [10, 11]},
  "team_2": {"team_id": "team_2", "side": "far", "track_ids": [20, 21]},
  "unassigned_track_ids": [],
  "touches": [
    {"track_id": 10, "team_id": "team_1", "kind": "serve", "frame_index": 310, "time_sec": 10.333333, "status": "estimated"},
    {"track_id": 20, "team_id": "team_2", "kind": "dig", "frame_index": 370, "time_sec": 12.333333, "status": "estimated"},
    {"track_id": 21, "team_id": "team_2", "kind": "attack", "frame_index": 460, "time_sec": 15.333333, "status": "estimated"}
  ],
  "surface_contacts": [
    {"frame_index": 540, "time_sec": 18.0, "surface": "floor", "outcome": "near_half", "status": "estimated"}
  ],
  "winning_team": "team_2",
  "point_reason": "ball_in_opponent_court",
  "point_status": "estimated",
  "analysis_status": {
    "tracks": "ready",
    "teams": "ready",
    "touches": "ready",
    "point": "ready",
    "identities": "pending"
  }
}
```

Время — абсолютное в анализируемом видео по frame_index и таймбазе подготовленного источника (в примере 30 FPS); оригинальное время через существующее отображение источника, не через предположение о FPS оригинала. Все события внутри границ розыгрыша; неизменяемый идентификатор события включает источник, кадр и тип контакта. player_id добавляется при чтении в состав и события по актуальной ревизии привязок (null до привязки). Не заменять track_id на player_id. События с неизвестным участником или типом сохранять с null / unknown_touch, не выбрасывать. Типы по ActionKind: serve, dig, overhead_pass, attack, block; неразрешённое low_touch не выдавать за dig. Статус результата: estimated, confirmed, unknown; статус этапа: pending, ready, unavailable. Неизвестный результат — null, не фиктивное значение. Подача хранится только как событие touches с kind = serve; подающий, команда и время извлекаются из этого события. Если момент подачи установлен, но ID неизвестен, track_id = null; если сам момент не установлен, событие не выдумывается. Отсутствие serve после завершения этапа touches означает, что подача не определена. Ручное исправление учитывается как отдельная ревизия и имеет приоритет.

## Формирование по ходу анализа

| Этап | Заполняемые данные |
| --- | --- |
| Границы розыгрыша | rally_id, start_frame, end_frame |
| Склейка рамок, позы, окончательная непрерывность треков | подготовка устойчивых ID для распределения по командам; отдельный список или счётчик в metadata не сохраняются |
| Геометрия площадки и принадлежность | team_1, team_2, unassigned_track_ids; голоса по наблюдаемому положению ног/нижней точке рамки и калиброванным половинам на протяжении розыгрыша |
| Ball Stabilizer → Touch Detector | хронология физических контактов только внутри розыгрыша; поверхность отделена от игрока |
| Типизация и контекст розыгрыша | touches.kind; ровно одна подача при достаточных данных; начальную траекторию использовать как гипотезу, уточнять по появившемуся игроку, не присваивать произвольный ID; исключить подброс из игровых касаний |
| Детектор пола/сетки и завершения | surface_contacts, winning_team, point_reason |
| ReID / ручная привязка | player_id; обновление представлений без повторного GPU-анализа |

Устойчивость: на входе окончательно объединённые Track ID, только реальные наблюдения, интерполированные кадры не увеличивают устойчивость. Требуются временная поддержка и отсутствие конфликтов одновременного присутствия; конкретные пороги должны быть версионированы, проверены на размеченных розыгрышах и не подбираться для принудительного получения ожидаемого числа игроков. Составы team_1.track_ids и team_2.track_ids — единственный источник истины для распределённых игроков. Каждый список уникальный и сортированный. Количество игроков вычисляется из длин списков команд, не хранится отдельно; временно нераспределённые устойчивые ID сохраняются только в unassigned_track_ids и учитываются при выводе общего числа с отметкой о неполном составе. Полностью готовый состав не содержит нераспределённых ID. Отдельные stable_track_count и stable_track_ids не входят в metadata; прежний модальный счёт допустим только как диагностика/legacy, не как источник состава. Игроки без касаний входят в состав. Редкое достоверное касание нестабильного трека не удалять; помечать неизвестную принадлежность.

Смена сторон не меняет team_id. До надёжного установления соответствия стороны команде не назначать team_id угадыванием. Игрок не может состоять в обеих командах в одном розыгрыше; двусмысленные треки попадают в unassigned_track_ids.

## Очко

Использовать первое достоверное терминальное событие, а не последующие отскоки. Мяч упал в пределах площадки (в том числе на линии) — очко противоположной команде. Вне площадки — очко команде, противоположной команде последнего достоверного игрового касания, включая блок. Касание сетки не само по себе завершение. При неопределённости линии, последнего касания, соответствия команды стороне или возможном нарушении без достаточных свидетельств — winning_team = null, point_status = unknown. Последующий отскок не начисляет ещё одно очко. Не выдавать геометрическую гипотезу за решение судьи.

## Разрыв между текущей реализацией и целью

В проверенном SHA stable_track_count — мода ненулевого количества наблюдаемых треков в кадре, а не длина списка устойчивых ID. court_contact_context содержит serve_track_id, serve_frame, side и events, но строится только при наличии стороны в истории контактов; primary_only путь создаёт пустые CourtHistory и surface_events. Поэтому добавление полей только в write_proposal без наполнения обоих путей не удовлетворяет контракту. Не переносить расчёт в предпросмотр: использовать единый CPU-владелец, проверенные треки, канонический Touch/Surface stream и соответствие источников. Переигрывать сохранённые CPU/GPU evidence при наличии нужных наблюдений; старые записи без metadata явно помечать как legacy.

## Критерии приёмки реализации

- Один и тот же результат для primary и CPU reconstruction при одинаковом наборе свидетельств и границ.
- Краткий лишний трек и интерполированный пропуск не увеличивают состав; игрок без касания остаётся в составе; число игроков вычисляется из уникальных составов команд и временно нераспределённых ID, без дублирующих полей.
- Команды непересекающиеся, смена половин не меняет team_id; отсутствие калибровки не создаёт ложную команду.
- Подача отражена только в единственном первом игровом событии touches с kind = serve; отдельное поле serve отсутствует, подброс исключён. Неизвестные ID не выдумываются.
- Первый удар об пол на линии и следующий за пределами поля дают только одно очко; out с неизвестным последним касанием остаётся unknown. Пол и сетка никогда не входят в touches.
- Смена привязки игрока меняет только проекцию identity; все потребители используют один снимок и ревизию.
- Проверить сериализацию/валидацию, несовместимость источников, чтение legacy, атомарность/отмену и оба пути публикации; отдельная проверка качества на размеченных видео, не на пользовательском проекте как фикстуре.
